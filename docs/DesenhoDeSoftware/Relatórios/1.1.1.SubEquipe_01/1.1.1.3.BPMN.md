### Metodologia 
O trabalho foi realizado com foco no fluxo de autenticação via Gov.br, analisando-o sob uma perspectiva de cibersegurança. Para isso, conduzimos uma experimentação prática no aplicativo Meu SUS Digital e baseamos nossas análises na **documentação de integração do login único do Gov.br**, bem como no padrão **OAuth 2.0 com PKCE especificado na RFC 7636** e nas diretrizes de segurança mobile da **OWASP**. Utilizamos a ferramenta [BPMN Sketch Miner](https://www.bpmn-sketch-miner.ai/) para criar rapidamente os modelos baseados em texto, facilitando o mapeamento iterativo das trocas de informações, como tokens JWT e redirecionamentos.

### Processo de Engenharia Reversa Aplicado
A Engenharia Reversa foi aplicada sob uma perspectiva comportamental (caixa-preta). Simulamos um login real no aplicativo Meu SUS Digital usando uma conta Gov.br, interceptando visualmente as etapas (redirecionamentos de navegador) e analisando o padrão arquitetural esperado para esse tipo de integração, que é o OAuth 2.0 com PKCE (Proof Key for Code Exchange).

Os achados revelaram que o Frontend do Meu SUS Digital interage com o Gov.br gerando códigos de desafio (Code Verifier e Challenge), enviando-os no Backchannel, recebendo os Tokens e validando as assinaturas (JWKS) antes de permitir o acesso seguro ao painel do Cidadão.

### Modelagem BPMN
O modelo gerado detalha o fluxo de Autenticação entre o Cidadão, o Frontend (Meu SUS Digital) e o provedor Gov.br.
### Detalhamento do Fluxo de Autenticação (OAuth 2.0 + PKCE)

A tabela abaixo detalha as responsabilidades de cada componente e as justificativas arquiteturais e de cibersegurança para cada etapa e decisão (gateways) modeladas no BPMN.

| Ator (Raia) | Elemento BPMN (Ação / Decisão) | Justificativa de Engenharia e Cibersegurança |
| :--- | :--- | :--- |
| **Cidadão** | Inicia login pelo app Meu SUS Digital | Ponto de partida do fluxo de usuário (Gatilho do caso de uso). |
| **Frontend** | Gera Code Verifier (alta entropia) | Criação de um segredo criptográfico temporário e exclusivo para esta sessão. Sendo um SPA/App Mobile, o cliente é considerado "público" e não pode armazenar um *Client Secret* fixo com segurança ([RFC 8252](https://datatracker.ietf.org/doc/html/rfc8252)). |
| **Frontend** | Aplica SHA-256 gerando Code Challenge | O uso do algoritmo de hash unidirecional (SHA-256) garante que o provedor (Gov.br) receba a "prova" do segredo sem que o próprio segredo trafegue na URL inicial (Mitigação contra *Authorization Code Interception*, [RFC 7636](https://datatracker.ietf.org/doc/html/rfc7636)). |
| **Frontend** | Envia requisição de autorização HTTPS | O uso estrito de TLS (HTTPS) na conexão de *frontchannel* (navegador/app) protege os parâmetros da URL contra *Sniffing* e interceptação passiva. |
| **Gov.br** | Analisa risco e credenciais | Implementação de heurísticas de segurança (ex: análise de IP, *fingerprint* do dispositivo e falhas sucessivas) para mitigar ataques de força bruta ou *Credential Stuffing*. |
| **Gov.br** | **Gateway:** Acesso permitido? (Não) | Bloqueia o acesso precocemente para economizar recursos computacionais e registra o evento em logs de auditoria para monitoramento de incidentes. |
| **Gov.br** | Gera Authorization Code (TTL 60s) | O código gerado possui um tempo de vida (Time-To-Live) curtíssimo. Isso reduz drasticamente a janela de oportunidade caso o código seja vazado pelo histórico do navegador ou logs do sistema operacional. |
| **Frontend** | Envia POST no *Backchannel* com Code e Verifier | A troca do Código pelo Token ocorre nos bastidores, fora do alcance do usuário. O envio do *Verifier* original prova ao Gov.br que quem está pedindo o token é exatamente o mesmo cliente que iniciou o login. |
| **Gov.br** | **Gateway:** Validação PKCE confere? (Não) | Se os hashes não baterem, o Gov.br identifica um ataque de **Interceptação de Código de Autorização** e encerra a comunicação (HTTP 401). |
| **Gov.br** | Assina JWT com RS256 e Retorna Tokens | O Gov.br gera o Access Token (para consumo de API) e o ID Token (dados do cidadão), assinando-os digitalmente com uma chave privada assimétrica (RS256) para garantir a integridade (Padrão [JWS - RFC 7515](https://datatracker.ietf.org/doc/html/rfc7515)). |
| **Frontend** | Busca chave JWKS e valida assinatura | O aplicativo consome a chave pública do Gov.br (JWKS) para atestar que o Token não foi alterado em trânsito e foi de fato emitido pelo provedor de identidade do governo (Requisito do [Manual de Integração Gov.br](https://manual-roteiro-integracao-login-unico.servicos.gov.br/)). |
| **Frontend** | **Gateway:** Tokens são autênticos? (Não) | Proteção vital contra ataques de **Man-in-the-Middle (MitM)**. Qualquer token com assinatura inválida, expirado ou com *Issuer* incorreto é imediatamente descartado. |
| **Frontend** | Salva tokens em Secure Storage | O uso de armazenamento criptografado nativo (como *Keychain* no iOS ou *Keystore* no Android) previne o roubo do token de sessão por outros aplicativos maliciosos ou scripts (XSS), seguindo recomendações da [OWASP Mobile Top 10](https://owasp.org/www-project-mobile-top-10/). |
| **Frontend** | Consome API do Meu SUS autenticada | Envio do Access Token no cabeçalho `Authorization: Bearer` para garantir que apenas usuários validados acessem o Prontuário Eletrônico do cidadão. |

### Referências 
* [RFC 7636 - Proof Key for Code Exchange by OAuth Public Clients](https://datatracker.ietf.org/doc/html/rfc7636)
* [RFC 8252 - OAuth 2.0 for Native Apps](https://datatracker.ietf.org/doc/html/rfc8252)
* [Manual de Integração Login Único Gov.br](https://manual-roteiro-integracao-login-unico.servicos.gov.br/)
* [OWASP Mobile Security Project](https://owasp.org/www-project-mobile-top-10/)
